# GEO（生成式引擎优化）智能管理系统 —— 最终菜单及功能设计方案

本方案结合若依（RuoYi-Vue-Plus）微服务框架规范，对系统的菜单结构进行扁平化改造，并对核心业务功能进行了系统性梳理。

为了降低用户的认知摩擦和操作成本，方案进行了三项核心调整：
1. **菜单结构扁平化**：移除深层嵌套的菜单，将系统层级统一控制在 **二级目录** 内，使用户查找功能更加快捷。
2. **去戏剧化命名**：将原本过于拟物化、文学色彩偏重的名称重构为严谨、直白的高效中后台管理术语。
3. **功能高度整合与收容**：
   *   将“AI智能拓词”和“规则拼词工具”收容为辅助生成工具，合并进“派生标题管理”页面，不占用左侧菜单路由。
   *   将“单篇复刻”和“批量复刻”深度整合为统一的“爆文复刻中心”菜单页面，通过同一个工作台的单篇/批量 Tab 切换操作，精简菜单层级。

### 📊 1. GEO诊断中心 (GEO Diagnostic Center)

#### 1.1 🔍 曝光度诊断 与 1.4 📜 诊断历史记录 (Diagnostic Engine & History)
*   **业务说明与技术方案**：
    这是整个 GEO 优化体系的“体检仪”。用户提交想要诊断的品牌词和行业主词，选择要测试的大模型平台。
    *   **无头浏览器探针集群 (Playwright Cluster)**：由于大模型问答页面（如 DeepSeek、豆包）属于高度动态渲染的 SPA 页面，且有反爬盾（如 Cloudflare / Geetest），系统后端微服务采用异步任务模式，下发任务至 RabbitMQ。独立的 Node.js/Python 探针集群订阅队列，调用 Playwright 无头浏览器加载真实的静态代理 IP，自动输入提问，等待 AI 回答渲染完毕，提取回答正文中的文本、被引用的脚注直链，并截取整个对话的完整高度长图上传至阿里云 OSS。
    *   **文本语义倾向分析 (Sentiment Mining)**：获取到 AI 回答文本后，利用轻量级自然语言处理模型或大模型 API 分析对目标品牌的提及倾向（褒义、中性、贬义）及推荐排名，存入明细表。
*   **字段界定与设计**：
    *   主表 `geo_diag_task` 管理单次诊断批次；明细表 `geo_diag_result` 存储每个大模型平台在不同关键词下的回答、引用外链列表及截图。
*   **页面布局推荐**：
    *   **即时发起页**：类 Google 搜索极简框，多选平台，点击一键诊断，进入加载态并带有 Playwright 执行日志小浮窗。
    *   **诊断详情报告页**：双栏布局，左侧为大模型对各词的提及率仪表盘、褒贬分析饼图；右侧点击可直接调出大模型提问回答的**真实高精度长截图快照**。
*   **建表 SQL 设计**：
    ```sql

      `task_id` bigint(20) NOT NULL COMMENT '主键ID',

      `industry_word` varchar(150) NOT NULL COMMENT '关联查询的行业核心词',
      `need_suggest` varchar(20) NOT NULL COMMENT '是否生成AI优化建议报告',
      `platforms` varchar(250) NOT NULL COMMENT '所选大模型平台',
      `status` varchar(20) NOT NULL COMMENT '状态',
      `fail_reason` varchar(500) DEFAULT NULL COMMENT '任务失败原因说明',
      `del_flag` char(1) DEFAULT '0' COMMENT '删除标志(0代表存在 2代表删除)',
      `create_dept` bigint(20) DEFAULT NULL COMMENT '创建部门',
      `create_by` bigint(20) DEFAULT NULL COMMENT '创建者',
      `create_time` datetime DEFAULT NULL COMMENT '创建时间',
      `update_by` bigint(20) DEFAULT NULL COMMENT '更新者',
      `update_time` datetime DEFAULT NULL COMMENT '更新时间',
      `remark` varchar(500) DEFAULT NULL COMMENT '备注',
      PRIMARY KEY (`task_id`)
    ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='GEO可见度诊断任务主表';

    -- 2. 曝光度诊断大模型回答明细表
    CREATE TABLE `geo_diag_result` (
      `result_id` bigint(20) NOT NULL COMMENT '明细主键ID',
      `task_id` bigint(20) NOT NULL COMMENT '关联诊断任务ID',
      `platform_type` varchar(20) NOT NULL COMMENT '大模型平台',
      `query_text` varchar(500) NOT NULL COMMENT '提问的完整Prompt',
      `answer_content` text DEFAULT NULL COMMENT 'AI返回的完整回答正文',
      `mention_status` varchar(20) NOT NULL COMMENT '品牌提及状态',
      `mention_rank` int(11) DEFAULT '0' COMMENT '品牌在回答推荐中的名次',
      `cited_urls` text DEFAULT NULL COMMENT '回答所引用的外链直链列表',
      `snapshot_url` varchar(500) DEFAULT NULL COMMENT '对话全高长截图OSS直链',
    ```

#### 1.2 👥 竞品能见度监控 (Competitor Visibility Radar)
*   **业务说明与技术方案**：
    对本品牌与竞品在主流 AI 大模型搜索中的被推荐率进行长期追踪对比。
    *   **定时轮询比对算法**：运营人员配置监控规则（选择核心词、输入 1-5 个竞品名称、配置周/月 Cron 表达式）。系统定时调度 Playwright 探针对各个大模型提问，获取回答。
    *   **提及率对比分析**：系统后台扫描回答文本，如果出现竞品 A 的名字，则竞品 A 提及数加 1。最后在前端渲染时，汇总出“我方品牌 vs 竞品品牌”在大模型搜索引用中的份额百分比。
*   **字段界定与设计**：
    *   `geo_competitor_monitor` 管理定时规则监控配置；`geo_competitor_result` 存储按时间周期统计的历史占比数据。
*   **页面布局推荐**：
    *   对比折线图/雷达图（同屏对比我方与多款竞品的提及率历史波动）；下方为自动生成的竞争态势诊断报告卡（如：*“竞品A本周提及率上涨 15%，主要归功于其在小红书发文被大模型采纳”*）。
*   **建表 SQL 设计**：
    ```sql
    -- 1. 竞品监控规则配置表
    CREATE TABLE `geo_competitor_monitor` (
      `monitor_id` bigint(20) NOT NULL COMMENT '监控ID',
      `brand_name` varchar(150) NOT NULL COMMENT '我方品牌名称',
      `competitor_names` varchar(500) NOT NULL COMMENT '竞品品牌列表',
      `keyword_id` bigint(20) NOT NULL COMMENT '关联核心词ID',
      `cron_expression` varchar(100) DEFAULT NULL COMMENT '自动监控周期Cron表达式',
      `last_run_time` datetime DEFAULT NULL COMMENT '上次执行时间',
      `status` varchar(20) NOT NULL COMMENT '状态(0运行中 1停用)',
      `del_flag` char(1) DEFAULT '0' COMMENT '删除标志(0代表存在 2代表删除)',
      `create_dept` bigint(20) DEFAULT NULL COMMENT '创建部门',
      `create_by` bigint(20) DEFAULT NULL COMMENT '创建者',
      `create_time` datetime DEFAULT NULL COMMENT '创建时间',
      `update_by` bigint(20) DEFAULT NULL COMMENT '更新者',
      `update_time` datetime DEFAULT NULL COMMENT '更新时间',
      `remark` varchar(500) DEFAULT NULL COMMENT '备注',
      PRIMARY KEY (`monitor_id`),
      KEY `idx_keyword_id` (`keyword_id`)
    ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='GEO竞品可见度监控配置表';

    -- 2. 竞品提及率历史统计表
    CREATE TABLE `geo_competitor_result` (
      `comp_result_id` bigint(20) NOT NULL COMMENT '结果ID',
      `monitor_id` bigint(20) NOT NULL COMMENT '关联监控配置ID',
      `record_date` date NOT NULL COMMENT '记录日期',
      `my_mention_rate` decimal(5,2) DEFAULT '0.00' COMMENT '我方品牌提及率',
      `competitor_rates` text DEFAULT NULL COMMENT '竞品提及率明细',
      `del_flag` char(1) DEFAULT '0' COMMENT '删除标志(0代表存在 2代表删除)',
      `create_dept` bigint(20) DEFAULT NULL COMMENT '创建部门',
      `create_by` bigint(20) DEFAULT NULL COMMENT '创建者',
      `create_time` datetime DEFAULT NULL COMMENT '创建时间',
      `update_by` bigint(20) DEFAULT NULL COMMENT '更新者',
      `update_time` datetime DEFAULT NULL COMMENT '更新时间',
      `remark` varchar(500) DEFAULT NULL COMMENT '备注',
      PRIMARY KEY (`comp_result_id`),
      KEY `idx_monitor_date` (`monitor_id`,`record_date`)
    ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='GEO竞品提及率历史统计表';
    ```

    *   **截图资源索引**：在明细表 `geo_diag_result` 已经包含了截图地址。截图库页面主要是将这些图片资源进行聚合，提供按日期、大模型平台、诊断关键词过滤筛选。提供一键打包下载为 `.zip` 的功能，用于汇报演示。
*   **建表 SQL 设计**：

#### 1.5 📉 流量与收录报表 (Traffic & Citation Reports Dashboard)
*   **业务说明与技术方案**：
    该页面是一个集成的 GEO 可视化收录数据中心大屏（BI Dashboard）。
    *   **指标汇聚与计算引擎**：系统不需要为本报表创建重叠的数据实体表，以免数据不一致。而是通过编写高效的 **MySQL 视图 (Views)** 或 MyBatis 聚合 SQL，定时每天凌晨对 `geo_diag_result`（诊断明细表）和 `geo_keyword_trend`（指数趋势表）进行归纳汇总，计算得到：全网总收录率、大模型推荐词均位名次、外链渠道生效转化率等。
    *   **可视化呈现**：后端提供统计聚合 API。前端利用 ECharts 插件绘制出酷炫的 GEO 可见度趋势漏斗图、模型占比雷达图、以及词云图（展示被大模型提及频率最高的词汇实体），为企业用户提供科学的 GEO 优化成效实证展示。

### 🎯 2. 策略词库中心 (Keyword Strategy Center)

#### 2.1 🏷️ 核心词管理 (Core Keyword Management)
*   **业务说明**：集中维护管理用作 GEO 优化的核心源词与公司/品牌名称的映射。它是后续 AI 自动生成文章标题、爆文复刻、批量文章写作以及可见度诊断的顶层维度和核心实体。
*   **字段界定与设计**：
    *   `keyword_id` (`bigint`)：主键ID（雪花ID）。
    *   `keyword` (`varchar(150)`)：**核心关键词**（必填。如：`CRM系统`，用作大模型检索和文章SEO优化的核心触发词）。
    *   `company_name` (`varchar(150)`)：**公司/品牌名称**（必填。如：`织信软件`，用作提及率评估与回答意图转化的大纲主标）。
    *   `keyword_type` (`varchar(20)`)：分类标签（`1`品牌词，`2`产品词，`3`行业词，`4`竞品词。使用若依字典 `geo_keyword_type` 维护）。
    *   `status` (`varchar(20)`)：启用状态（`0`启用，`1`停用，便于批量写作任务和定时诊断时过滤）。
    *   `remark` (`varchar(500)`)：备注说明。

#### 2.2 📊 搜索热度指数 (Search Popularity Index)
*   **一、 名词定义与功能边界**
    *   **1. 传统搜索指数 (Traditional Search Index)**：代表该关键词在传统搜索引擎（如百度指数、微信指数、Google Trends）中的月度/日度搜索热度。由第三方 SEO 数据接口（如 5118 API、站长之家 API）或系统爬虫拉取。
    *   **2. GEO 检索指数 (GEO/LLM Index)**：代表该关键词在大语言模型搜索引擎（如 Perplexity, ChatGPT Search, 秘塔 AI 搜索, 豆包）中被用户提问和检索的估算频次。由于 LLM 厂商不公布检索指数，本系统采用 **「语义热度估算模型」** 综合计算得出（计算因子包括：核心词诊断触发频次、派生长尾词数量、各大模型语义相关词库的月度查询权重等）。
    *   **3. 优化黄金机会得分 (Opportunity Score)**：系统的核心建议指标，范围 `0 - 100`。
        $$\text{Opportunity Score} = \text{GEO 检索指数} \times \left(1 - \frac{\text{竞品可见度}}{100}\right) \times \text{行业相关度权重}$$
        分数越高，代表该词“大模型搜索热度大，但目前竞品在 AI 回答中尚未占领提及率”，是极具优化价值的 **「黄金关键词」**，运营人员应当优先围绕该词进行创作。
    *   **功能边界界定**：
        *   *在边界内（做）*：汇总展示关键词历史指数趋势；计算各核心词的优化机会排名；每半月或单次手动触发第三方 API 数据同步。
        *   *在边界外（不做）*：本功能不做“实时（秒级）用户检索量追踪”，因为主流搜索引擎指数均为 T+1 日更，且外部 API 有频次限制。
*   **二、 数据获取与详细计算方案**
    由于大模型厂商对搜索提问频次数据高度保密，系统采用 **「多源数据融合拟合算法」**，具体实现从以下三个维度进行数据获取与清洗：
    
    ##### 1. 原始数据源获取途径 (Data Sources)
    *   **数据源 A：传统搜索引擎检索基数 (Base traffic)**
        *   *数据指标*：百度搜索指数（Baidu Index）、谷歌月度检索量（Search Volume）。
        *   *获取方式*：后端定时任务（每半月执行一次）调用 **5118「关键词移动端/PC端检索量API」** 或 **站长之家「百度指数查询API」**，获取基础月度检索数值 $S_{raw}$。
    *   **数据源 B：口语化提问衍生率 (Conversational Intent Density)**
        *   *数据指标*：核心关键词关联的“长尾疑问词”数量和热度。大模型检索多数为完整句子（如：“CRM系统哪个好用？”而非“CRM系统”）。
        *   *获取方式*：调用 **5118「需求图谱/疑问词挖掘API」**。传入核心词，API 会返回百度知道、知乎等全网用户真实的提问列表及检索量。系统统计出：① 疑问词总数 $Q_{count}$；② 疑问词关联检索量均值 $Q_{val}$。
    *   **数据源 C：系统内部 LLM 探针诊断反馈 (RAG Citation Rate)**
        *   *数据指标*：大模型在回答此词相关诊断时，触发联网搜索（RAG）并引用网页链接的概率。
        *   *获取方式*：通过系统本地 `geo_diag_task`（曝光度诊断）历史表，聚合过去 30 天该关键词的所有诊断批次，统计得到：① 触发联网引用链接的比例 $R_{rag}$（0.0 - 1.0）；② AI 回答的平均字符长度 $L_{ans}$。
        
    ##### 2. GEO 检索指数计算模型算法 (Algorithm & Code logic)
    系统对获取到的三路数据，进行归一化及对数降噪处理，防止超高热度词（如“AI”）扭曲指数分布。计算公式如下：
    
    $$S_{base} = \log_{10}(S_{raw} + 1) \times 100 \quad \text{（基础流量对数转换，基准区间 0 - 800）}$$
    $$Q_{density} = \log_{10}(Q_{count} \times Q_{val} + 1) \times 50 \quad \text{（口语提问密集度）}$$
    $$R_{rag\_factor} = R_{rag} \times 100 \quad \text{（大模型检索依赖度，无诊断数据时默认取 0.5 作为常数基准）}$$
    
    $$\text{最终 GEO 检索指数 } (\text{LLM\_Index}) = \omega_1 \cdot S_{base} + \omega_2 \cdot Q_{density} + \omega_3 \cdot R_{rag\_factor}$$
    
    *   *权重推荐配置*：$\omega_1 = 0.4$（传统热度），$\omega_2 = 0.3$（口语化提问度），$\omega_3 = 0.3$（大模型诊断依赖度）。
    *   *数据归一化*：计算结果乘以系数 $10$ 映射为常规指数表现（例如：`3540`、`12500` 等）。

#### 3.2 🔄 官网自学习同步 (Website Auto-learning Sync)
*   **业务说明与设计思路**：
    与“官网SEO同步”将系统内容向外推送的逻辑类似，本页面解决的是“如何将官网产生的新闻、产品特性等数据自动、安全地回收学习”的问题。本系统采用 **“图文反向抓取/接收适配器”** 架构，提供三种自学习同步模式，并且支持**直接复用已配置的官网站点凭证（`site_id`）**以简化操作：
    1.  **模式一：传统爬虫抓取 (Web Crawler)**：针对没有接口的传统网站，配置 Cron 定时任务，后端通过爬虫抓取网页 HTML，并通过配置 CSS 选择器过滤导航栏和页脚，智能清洗出主体正文。
    2.  **模式二：API 定时拉取 (API Pull)**：对于提供查询 API 的 CMS 网站，定时去请求对方的新闻列表接口，支持配置 HTTP Headers（可直接复用 `geo_website_config` 的凭证），利用 JSONPath 表达式（如 `$.posts[*].content`）批量提取正文及产品参数。
    3.  **模式三：Webhook 被动接收 (Webhook Push)**：本系统向外暴露一个标准的 API 被动接收端点（如 `/api/geo/webhook/learn`）。企业可以在官网 CMS 系统（如 WordPress 发布新文章时）配置 Webhook，一有内容更新就主动 POST 给本系统，系统自动解析并存入知识库。
*   **字段界定与设计**：
    *   `sync_id` (`bigint`)：主键ID（雪花ID）。
    *   `site_id` (`bigint`)：**关联的已配置官网站点ID**（可为空，关联 `geo_website_config` 表。关联后可自动复用其主域名、发文 API 秘钥及 Headers，无需重复配置验证信息）。
    *   `sync_name` (`varchar(150)`)：**同步任务名称**（必填，如：`官网产品新闻自学习`）。
    *   `sync_mode` (`varchar(20)`)：**同步模式**（`1` 传统爬虫抓取, `2` API定时拉取, `3` Webhook被动接收）。
    *   `source_url` (`varchar(500)`)：爬虫入口 URL / API 拉取直链地址。
    *   `cron_expression` (`varchar(100)`)：**定时同步周期**（如每天零点 `0 0 0 * * ?`。Webhook被动模式下无需此参数）。
    *   `crawler_selectors` (`varchar(500)`)：**正文提取 CSS 选择器**（爬虫模式下必填，如：`.article-content, #main-text`，用于提取正文）。
    *   `response_content_path` (`varchar(150)`)：**内容提取 JSONPath 表达式**（API模式下必填，如 `$.data.list[*].content`）。
    *   `status` (`varchar(20)`)：启用状态（`0`正常，`1`停用）。
*   **页面布局推荐**：
    *   **同步排程看板**：上方展示总体自学习统计卡片（已累计自学习篇数、提取有效字符数、上次同步时间）。下方为同步排程列表。
    *   **学习测试弹窗**：在新建或修改配置时，提供一键 `⚡ 模拟自学习` 按钮，展示抓取解析后的纯文本预览与切片，确保抓取规则配置无误后再入库。
*   **建表 SQL 设计**：

#### 4.1 📜 创作指令库 (Creative Prompt Library)
*   **业务说明**：本页面是定义和编排系统各模块 AI Agent 行为的核心配置中心。系统所有的智能化原子能力（如：`标题生成`、`智能拓词`、`编写文章`、`智能诊断分析` 等）其底层的 System Prompt 角色定义与 User Prompt 变量模版均在此配置。这使得业务规则的调整无需修改后端代码，极大提升了 Agent 的动态可调优性。
*   **字段界定与设计**：
    *   `template_id` (`bigint`)：主键ID（雪花ID）。
    *   `template_name` (`varchar(150)`)：**指令/Agent名称**（必填，如：`小红书爆文风格洗稿编写Agent`）。
    *   `template_code` (`varchar(50)`)：**指令唯一编码**（必填，英文字符，如：`AGENT_TITLE_GEN`、`AGENT_KEYWORD_EXP`、`AGENT_ARTICLE_WRITE`、`AGENT_DIAG_ADVISE`。后端通过该 Key 绑定并调用对应的模版规则）。
    *   `agent_type` (`varchar(20)`)：Agent功能类型（`1` 标题生成, `2` 智能拓词, `3` 文章编写, `4` 智能诊断分析, `5` 其它自定义。使用字典 `geo_agent_type` 维护）。
    *   `system_prompt` (`text`)：**System系统提示词**（定义 Agent 的专业角色定位、语气、排版约束等）。
    *   `user_prompt` (`text`)：**User用户模版提示词**（核心文本，支持变量占位符，例如：`请根据商品名 {item_name} 和核心卖点 {core_selling_points} 撰写一篇软文...`）。
    *   `model_name` (`varchar(50)`)：推荐调用大模型名称（如：`deepseek-chat`、`gpt-4o`、`qwen-max` 等）。
    *   `temperature` (`decimal(3,2)`)：创意度/温度系数（`0.00`至`1.00`之间的数值）。
    *   `status` (`varchar(20)`)：启用状态（`0` 启用，`1` 停用）。
*   **页面布局推荐**：
    *   **分栏卡片布局**：左侧为系统自带 Agent 指令（锁定不可修改，仅支持克隆）与用户自定义 Agent 分类树。右侧展示对应 Agent 的参数详情与 Prompt 输入框。

*   **建表 SQL 设计**：

#### 5.1 🎯 官网SEO同步 (Website SEO Sync)
*   **业务说明与架构设计**：
    由于不同企业使用的官方网站系统（CMS）多种多样，有的使用开源系统（如 WordPress, PbootCMS, EyouCMS 等），有的则是公司自研的专用 API。因此，本系统采用 **“可插拔驱动适配器 (Adapter Pattern)”** + **“自定义 Webhook 载荷映射器 (JSON Mapper)”** 架构进行设计，彻底解决不同 API 的兼容问题：
    1.  **内置标准 CMS 驱动**：出厂预设标准接口驱动，支持 WordPress 官方 REST API，以及针对 PbootCMS/EyouCMS 等国内主流 CMS 提供官方“免开发 PHP 对接适配脚本文件（用户直接下载并扔进网站根目录即可免密对接）”。
    2.  **自定义 Webhook 映射器**：对于完全自研接口的企业，支持其在 UI 界面自定义配置其 API 的 `HTTP Headers`、`Body 请求体 JSON 模版`（支持占位符替换，如 `{title}`, `{content}`），以及配置 `回执直链提取 JSONPath`（如 `$.data.articleUrl`，便于系统提取发布成功的文章真实链接并自动提交百度/谷歌爬虫收录）。
*   **字段界定与设计**：
    *   `site_id` (`bigint`)：主键ID（雪花ID）。
    *   `site_name` (`varchar(150)`)：**站点自定义名称**（必填，如：`织信科技中文官网`）。
    *   `site_url` (`varchar(250)`)：**网站主域名**（必填，如：`https://www.company.com`）。
    *   `cms_type` (`varchar(20)`)：**对接接口类型**（`1` WordPress标准API, `2` PbootCMS专用脚本, `3` EyouCMS专用脚本, `4` 自定义通用 Webhook）。
    *   `api_url` (`varchar(500)`)：**对接接口地址**（必填，指发文 API 的完整直链路径）。
    *   `http_headers` (`text`)：**自定义请求头**（选填，用于自定义 Webhook 鉴权，存储 JSON 字符串如 `{"Authorization": "Bearer tokenxxx"}`）。
    *   `body_template` (`text`)：**请求体 JSON 模版**（自定义 Webhook 模式下必填。支持参数占位符，如：`{"title": "{title}", "text": "{content}", "cate_id": "{target_cat_id}"}`）。
    *   `response_url_path` (`varchar(150)`)：**回执链接 JSONPath**（自定义 Webhook 模式下必填。系统用它来提取响应 JSON 中的发文直链，如：`$.data.url`）。
    *   `target_cat_id` (`varchar(100)`)：映射的对方栏目ID（如发往对方网站的“行业新闻”栏目）。
    *   `publish_status` (`varchar(20)`)：默认发布状态（`0`直接发布，`1`存为草稿）。
    *   `status` (`varchar(20)`)：启用状态（`0`正常，`1`停用）。
*   **页面布局推荐**：
    *   **站点对接配置页**：左边为已对接的官网列表，右边为详细表单。当选择 `4 自定义通用 Webhook` 时，表单动态展示 `HTTP Headers`、`Body 模版` 和 `JSONPath 解析规则` 输入框，并配有一键 `🔌 对接连通性测试` 按钮。

#### 5.2 📱 自媒体号管理 (Media Account Management)
*   **业务说明与技术方案**：
    对接微信公众号、小红书、知乎、百家号、今日头条等主流自媒体平台。主要解决**“多账号管理”**与**“平台防关联/封号控制”**两大难点：
    1.  **分渠道驱动模式**：对于微信公众号等有官方开发者接口的平台，系统采用 OAuth2.0 进行安全静默托管；对于小红书、知乎等无开放发文接口或接口流控严格的平台，系统采用 **“加密 Cookie 提取注水技术”**，在后台通过 Puppeteer/Playwright 模拟用户登录会话状态自动分发。
    2.  **独占静态代理 IP 隔离机制**：为防止平台通过发文 IP 识别出同一个“营销矩阵”而封杀关联账号，每一条绑定的自媒体通道都支持配置**专用的 Socks5/HTTP 静态代理 IP**。系统调度服务在启动无头浏览器发布时，会将该账号的 Proxy Host 与 User-Agent 绑定至当前浏览器上下文，确保每个账号的发布 IP 完全隔离。
*   **字段界定与设计**：
    *   `account_id` (`bigint`)：主键ID。
    *   `account_name` (`varchar(150)`)：**自媒体账号昵称**（必填）。
    *   `platform_type` (`varchar(20)`)：**平台类型**（`1` 微信公众号, `2` 百家号, `3` 知乎, `4` 小红书, `5` 今日头条）。
    *   `auth_type` (`varchar(20)`)：认证鉴权类型（`1` 官方授权凭证, `2` Cookie/Session凭证）。
    *   `app_id` / `app_secret` (`varchar(250)`)：针对 OAuth 模式的密钥串。
    *   `cookie_data` (`text`)：针对 Cookie 模式的密文凭证。
    *   `proxy_host` / `proxy_port` (`varchar(100)`/`int`)：绑定的独立静态代理网关。
    *   `status` (`varchar(20)`)：账号存活状态（`0` 登录存活, `1` 停用, `2` 授权过期需要重签）。
*   **页面布局推荐**：
    *   **多矩阵卡片网格**：每张卡片展示该自媒体号头像、平台图标、当前登录状态，并在底部带有 `⚡ 代理测速` 与 `🔄 续签登录` 按钮。
*   **建表 SQL 设计**：

#### 6.3 💳 财务账单 (Billing Logs)
*   **业务说明与技术方案**：
    负责统计账户点数/金额流水，提供充值记录与扣费防超卖保障。
    *   **高并发扣费防超卖控制**：大批量写作任务并发进行扣减算力时，必须防止并发数据读写脏读。系统采用**数据库行锁事务扣减**配合**扣减条件判断**：
        ```sql
        UPDATE geo_user_account 
        SET balance = balance - :cost 
        WHERE user_id = :userId AND balance >= :cost;
        ```
        只有当返回值影响行数（Affected Rows）大于 0 时，才扣费成功并向 `geo_billing_log` 表写入变动流水日志，否则抛出余额不足异常并回滚文章生成任务。
*   **字段设计**：
    *   `bill_id` (`bigint`)：主键ID。
    *   `user_id` (`bigint`)：系统用户ID。
    *   `order_no` (`varchar(100)`)：流水业务关联的充值单号/发文单号。
    *   `amount` (`decimal(10,2)`)：变动数（带符号：正数充值/退款，负数消费）。
    *   `bill_type` (`varchar(20)`)：类型（`1` 充值, `2` AI写作消费, `3` 媒体分发消费, `4` 驳回退款）。
    *   `balance` (`decimal(10,2)`)：本次流水变动后的实时卡内余额。
*   **建表 SQL 设计**：
